## 1. Vision

Un SaaS de menu QR digital et de commande à table pour les restaurants et cafés en Italie. Un client scanne le QR de sa table, consulte le menu depuis son téléphone (rien à installer) et commande — la commande arrive instantanément en cuisine et sur le dashboard du restaurant.

**Positionnement — TRANCHÉ : l'angle est la distribution, pas la fonctionnalité.**

Le produit reste une réplique fonctionnelle du cœur de marché (menu + commande + temps réel + staff + analytics). Ce qui différencie n'est pas ce que fait le logiciel, mais comment il arrive chez le client : acquisition payante alimentée par une preuve sociale réelle, construite avec un réseau de restaurateurs sur place.

**Atouts du fondateur :** présence en Italie + réseau de contacts dans la restauration. Ce sont ces deux éléments qui rendent le plan viable — pas une supériorité produit.

**Décision d'acquisition : publicité payante** (et non vente en direct par le réseau). Le réseau ne sert pas de canal de vente mais de **source de preuve sociale** : il produit les témoignages, vidéos et chiffres qui rendent les publicités rentables. Sans cette preuve, les créas d'un SaaS inconnu convertissent très mal.

## 5. Modèle de données (premier jet)

```
organizations (le "tenant" = un restaurant)
  id, name, slug, address, city, phone, logo_url,
  theme_color, default_language (it),
  subscription_plan, subscription_status, trial_ends_at

users (staff)
  id, organization_id → organizations, name, email,
  password_hash, role (owner/manager/server/kitchen),
  last_active_at

tables (tables physiques du restaurant)
  id, organization_id → organizations, label,
  qr_token (unique), status (free/occupied)

menu_categories
  id, organization_id → organizations, name_it, name_en, sort_order

menu_items
  id, category_id → menu_categories, organization_id → organizations,
  name_it, name_en, description_it, description_en,
  price, photo_url, is_available, sort_order,
  allergens (array — 14 allergènes UE, ex: gluten, lactose, fruits à coque...)

orders
  id, organization_id → organizations, table_id → tables,
  status (pending/in_progress/ready/served/cancelled),
  total_amount, created_at, updated_at

order_items
  id, order_id → orders, menu_item_id → menu_items,
  quantity, unit_price, notes

staff_calls (bouton "appeler le serveur")
  id, table_id → tables, status (pending/acknowledged), created_at

subscriptions
  id, organization_id → organizations, plan, status,
  payment_provider (stripe), external_subscription_id,
  current_period_end
```

Tout est scopé par `organization_id` — c'est la clé de l'isolation multi-tenant.

> **Implémenté en Phase 0 / étape 1 avec deux écarts par rapport à ce premier jet — voir §12.2** : `order_items` et `staff_calls` portent aussi un `organization_id` direct (pas seulement via leur FK parent), et une table `invitations` (absente d'ici) a été ajoutée pour le flux d'invitation du staff.

## 6. Stack technique

- **Frontend** (menu public + dashboard) : Next.js + Tailwind, mobile-first pour le menu public
- **Temps réel** : Socket.io ou Supabase Realtime pour le flux commande → cuisine
- **Backend** : Node/TS (API routes Next.js ou NestJS séparé)
- **Base de données** : PostgreSQL (Supabase ou Neon pour démarrer vite)
- **Auth staff** : Supabase Auth / Clerk — les clients qui commandent n'ont pas de compte
- **Stockage photos** : S3-compatible (Supabase Storage / Cloudflare R2)
- **Paiement/abonnement** : Stripe (pleinement supporté en Italie, contrairement à la Tunisie — pas de contournement nécessaire)
- **Notifications** : Web Push (statut commande, appel serveur)
- **Hébergement** : Vercel (front + edge) + Postgres managé, idéalement région UE (Frankfurt/Paris) pour la latence et la conformité RGPD

> **Précisions apportées en Phase 0 / étape 1 — voir §12.1** : API routes Next.js retenues (pas de NestJS séparé) ; auth staff maison (JWT + bcrypt) en attendant de rebrancher Supabase Auth/Clerk ; PostgreSQL avec Row-Level Security comme mécanisme d'isolation multi-tenant, quel que soit l'hébergeur choisi ensuite (Neon/Supabase, tous deux compatibles RLS).

## 7. Contraintes non-fonctionnelles

- **Latence** : la commande doit apparaître côté cuisine en moins de 2-3 secondes après validation client
- **Isolation multi-tenant** : aucune fuite de données entre restaurants
- **RGPD** : régime UE complet (plus strict que le cadre tunisien envisagé initialement) — base légale claire pour chaque donnée collectée, droit à l'effacement, hébergement UE recommandé
- **Allergènes** : conformité Règlement UE n°1169/2011 (14 allergènes à signaler clairement)
- **Multilingue dès le MVP** : italien + anglais au minimum
- **Résilience réseau** : le wifi resto n'est pas toujours fiable — comportement dégradé propre plutôt qu'un plantage silencieux

## 8. Pricing

**Modèle retenu : annuel prépayé, ~400 €/an.**

Raison : avec une acquisition payante, le coût d'acquisition client (CAC) est estimé entre 80 et 300 €. Un abonnement mensuel à 40 € oblige à financer 2 à 6 mois de trésorerie avant de rembourser l'acquisition de chaque client. L'annuel prépayé rembourse le CAC immédiatement.

**Arithmétique à valider par le test** (ordres de grandeur B2B, pas des prévisions) :

| Variable | Estimation |
|---|---|
| Durée de vie moyenne client | 10-15 mois (les petits restos churnent beaucoup) |
| Valeur client (LTV) brute | 400-600 € |
| Coût par lead (Meta, B2B resto Italie) | 5-30 € |
| Taux lead → client payant | 5-15 % |
| **CAC estimé** | **80-300 €** |
| Retour sur investissement | 4-8 mois en mensuel / immédiat en annuel |

Marge d'erreur faible : ces chiffres doivent être remplacés par les chiffres réels du test média (Phase C) avant tout engagement budgétaire sérieux.

Essai gratuit à définir.

**Correction — erreurs Postgres brutes mal gérées (signup en double, `npm run setup` relancé) : FAIT (27 juillet 2026).** Premier vrai test en local sur Windows (au-delà du simple lancement) : une inscription avec un email déjà utilisé renvoyait un 500 brut avec la stack trace Prisma au lieu d'un message propre, et relancer `npm run setup` une deuxième fois (pour redémarrer le serveur après un Ctrl+C, par exemple) faisait planter tout le script au moment du seed. Deux symptômes d'une même cause : `$queryRaw`/`$executeRaw` vers les fonctions `SECURITY DEFINER` (§12.3) enveloppent toujours l'erreur Postgres réelle dans un `PrismaClientKnownRequestError` de code `P2010` ("Raw query failed"), avec le vrai SQLSTATE et message dans `error.meta`, pas dans `error.message` — les vérifications par regex sur `error.message` dans `handleApiError` (`src/lib/api.ts`) ne matchaient donc jamais un vrai conflit de contrainte unique. Corrigé en inspectant `error.meta.code` (SQLSTATE `23505`/`23503`) au lieu du texte de `error.message`. Même cause côté `prisma/seed.ts` : le garde-fou "org déjà seedée, on saute" faisait un `findUnique` direct sans contexte de tenant (`app.current_org_id` non défini) — filtré à zéro ligne par la RLS (§12.3) quoi qu'il arrive, donc jamais déclenché. Remplacé par un `try/catch` autour de l'insertion elle-même, qui traite une violation de contrainte unique sur le slug comme "déjà seedé" — rend `npm run setup` réellement rejouable, ce qu'annonce le README depuis le début sans que ce soit vrai jusqu'ici.

## 12. Phase 0 / étape 1 — décisions d'architecture (fondations + multi-tenant)

Implémenté : projet Next.js 14 (App Router) + TypeScript + Prisma + PostgreSQL, isolation multi-tenant par Row-Level Security, signup restaurateur, invitation de staff par rôle, dashboard minimal par rôle, démarrage local en une commande (`npm run setup`).

### 12.1 Précisions sur la stack (§6) — pas de contradiction, des choix concrets faits

- **API routes Next.js, pas NestJS.** §6 laissait le choix ouvert. Un backend séparé n'apporte rien tant qu'il n'y a qu'une seule application cliente (le dashboard) — c'est de la complexité à justifier plus tard si un vrai besoin de découplage apparaît (ex. un service worker séparé pour le temps réel à fort volume).
- **Auth maison (JWT en cookie httpOnly + bcrypt), pas Supabase Auth/Clerk pour l'instant.** Le mécanisme de vérité — l'isolation — devait être prouvé au niveau de la base de données indépendamment de qui authentifie l'utilisateur. Écrire l'auth soi-même a permis de contrôler exactement ce qui se passe entre "l'utilisateur est authentifié" et "la policy RLS s'applique" (voir 12.3). Rebrancher Supabase Auth ou Clerk plus tard reste possible : il suffirait de leur faire émettre le même type de session (userId + organizationId + role) et de garder la même couche RLS — c'est le point d'intégration, pas un mur.
- **PostgreSQL avec Row-Level Security, indépendant de l'hébergeur.** Neon et Supabase supportent tous les deux RLS nativement ; ce choix ne ferme aucune porte sur l'hébergement UE (§12.4).

### 12.2 Écarts par rapport au premier jet du schéma (§5)

1. **`organization_id` dénormalisé sur `order_items` et `staff_calls`.** Le jet initial ne les scope qu'indirectement (via `order_id` / `table_id`). Une policy RLS a besoin d'une colonne sur la ligne elle-même pour filtrer efficacement — passer par une sous-requête vers la table parente à chaque lecture aurait fonctionné mais coûté cher en performance sur les tables les plus chaudes (commandes). Dénormaliser le `organization_id` est une pratique reconnue en multi-tenant Postgres avec RLS.
2. **Table `invitations` ajoutée**, absente du jet initial. Nécessaire pour que "inviter du staff" soit un vrai flux (lien à durée de vie limitée, rôle proposé, statut accepté/en attente) plutôt qu'un compte pré-créé avec un mot de passe à deviner.
3. **`users.email` est unique globalement**, pas seulement par organisation. Un membre du staff se connecte sans indiquer d'abord son restaurant — l'email doit donc être non ambigu à l'échelle du système. Limite connue : une même personne ne peut pas avoir un compte dans deux restaurants différents avec le même email (voir §13).

Le reste du schéma §5 (`tables`, `menu_categories`, `menu_items`, `orders`, `subscriptions`) est en place dans Prisma et protégé par RLS, mais sans logique métier ni UI — c'est le socle pour les prochaines étapes de la Phase 0, pas une fonctionnalité livrée.

### 12.3 L'isolation multi-tenant est une garantie Postgres, pas une convention de code

C'était la contrainte explicite de cette étape. Mécanisme :

- Le rôle applicatif (`app_user`, celui que Next.js utilise pour se connecter) ne possède aucune table et n'a pas l'attribut `BYPASSRLS`. Un rôle séparé (`app_migrator`) possède le schéma et exécute les migrations — voir `docker/init-roles.sql`.
- Chaque table scopée par organisation a une policy `USING / WITH CHECK (organization_id = current_setting('app.current_org_id'))`. Sans ce réglage de session, la policy s'évalue à `NULL` (donc "aucune ligne") — la position par défaut est "ne rien voir", pas "tout voir".
- Toute requête applicative passe par `withTenant(organizationId, ...)` (`src/lib/db.ts`), qui ouvre une transaction et fixe cette variable de session avant d'exécuter quoi que ce soit.
- Trois flux sont légitimement antérieurs à tout contexte de tenant (inscription, connexion, acceptation d'invitation) et ne peuvent pas passer par une transaction scopée — chacun a sa propre fonction Postgres `SECURITY DEFINER`, étroite et à usage unique, plutôt qu'un contournement large de RLS pour tout le rôle applicatif.
- **Preuve automatisée** : `tests/isolation.test.ts` crée deux organisations et vérifie, au niveau de la base (pas via l'API), que ni une lecture ni une écriture ne peuvent franchir la frontière — y compris dans le cas d'un bug applicatif simulé (une requête qui "oublie" de filtrer par organisation).

### 12.4 Hébergement UE (RGPD)

Non tranché à ce stade (cohérent avec §10, question ouverte non bloquante), mais cadré : le choix se fera entre Neon et Supabase, tous deux avec des régions Francfort, et tous deux compatibles avec le modèle RLS mis en place ici — donc pas de retour en arrière architectural à prévoir quel que soit le choix final.

### 12.5 QR + commande client (étape 3) — le même schéma de contournement étroit, étendu au client final

Le client qui scanne un QR n'a ni compte ni session : c'est la même catégorie de problème que l'inscription/connexion/invitation (§12.3), avec la même solution. Une seule fonction `SECURITY DEFINER` de plus, `resolve_table_by_qr_token`, qui transforme le `qr_token` d'une table en `organization_id`. **Une fois cet identifiant connu, tout le reste — lire le menu, insérer la commande — passe par le `withTenant()` RLS-scopé normal, exactement comme une écriture faite par le staff.** Il n'y a pas de fonction `SECURITY DEFINER` pour créer une commande : la garantie `WITH CHECK` de RLS suffit, une fois qu'on est dans le bon tenant.

**Prix jamais fait confiance au client** : le prix facturé est relu depuis `menu_items` au moment de la commande, dans la même transaction qui crée la commande — un client qui manipule la requête HTTP pour envoyer un prix différent n'a aucun effet, le schéma de validation n'accepte même pas de champ prix côté commande.

**Durcissement supplémentaire découvert pendant cette étape** : RLS garantit qu'une organisation ne peut pas *lire* les tables d'une autre, mais ne garantit pas, à elle seule, qu'une ligne `orders` ne puisse pas *pointer* vers une table d'une autre organisation (une commande avec `organization_id` correct mais `table_id` d'un autre tenant serait acceptée par la policy RLS, qui ne vérifie que la colonne `organization_id`). Corrigé par des **clés étrangères composites** : `orders.table_id` référence désormais `tables(id, organization_id)` et non plus `tables(id)` seul (même traitement pour `menu_items.category_id`, `order_items.order_id`, `order_items.menu_item_id`, `staff_calls.table_id`). La base rejette maintenant nativement toute ligne où les deux tenants ne correspondent pas — plus une propriété qu'on espère du code applicatif, une contrainte que Postgres impose à l'écriture. Voir `prisma/migrations/*_composite_tenant_foreign_keys`.

### 12.6 Temps réel (étape 4) — Postgres `LISTEN`/`NOTIFY` + Server-Sent Events, pas Socket.io

§6 envisageait Socket.io ou Supabase Realtime. Ni l'un ni l'autre n'a été retenu pour cette étape :

- **Socket.io** suppose un serveur Node avec connexions WebSocket persistantes — cohérent avec `next start` en un seul processus, mais ajoute une dépendance et un protocole de plus alors que le besoin réel ("le staff voit une commande apparaître sans recharger la page") ne demande pas de canal bidirectionnel.
- **Supabase Realtime** suppose d'être hébergé chez Supabase, ce qui n'est pas encore tranché (§12.4 — Neon est toujours une option).

**Choix retenu** : un trigger Postgres (`prisma/migrations/*_order_realtime_notify`) appelle `pg_notify('order_events', ...)` à chaque création ou changement de statut d'une commande. Le serveur Next.js maintient une seule connexion Postgres dédiée en écoute (`LISTEN`, `src/lib/realtime.ts`) pendant toute sa durée de vie, et relaie chaque notification aux navigateurs connectés via **Server-Sent Events** (`GET /api/orders/stream`, une réponse HTTP en flux continu, pas de librairie externe). Le navigateur reçoit l'événement puis rappelle `GET /api/orders` — pas de fusion d'état incrémentale côté client, juste "quelque chose a changé, relis tout", volontairement simple pour cette étape.

C'est cohérent avec le reste de l'architecture : la base est déjà la source de vérité pour l'isolation (RLS) ; ici elle devient aussi la source de vérité pour "quoi notifier" — pas un bus de messages séparé à garder synchronisé avec elle.

**Limite connue, documentée plutôt que cachée** : ce mécanisme suppose un processus Node long-vivant (vrai pour `next dev` / `next start`, et pour tout hébergeur type Railway/Fly/VM classique). Une fonction serverless (Vercel Functions dans sa forme par défaut) ne maintient pas de connexion `LISTEN` persistante entre les invocations — il faudrait soit un petit service Node dédié à cette seule connexion, soit un service temps réel géré (Supabase Realtime, Pusher). Pas un problème pour valider le produit en pilote ; à trancher en même temps que l'hébergement définitif (§12.4).

### 12.7 Stripe (étape 5) — codé, vérifié hors-ligne, jamais exercé en vrai

**Ce qui a pu être vérifié sans compte Stripe réel :**
- Le webhook (`POST /api/billing/webhook`) a été testé avec un événement `customer.subscription.updated` signé localement (la vérification de signature Stripe est un simple HMAC, elle ne nécessite aucun appel réseau) : signature valide → statut d'organisation et ligne `subscriptions` correctement mis à jour ; signature invalide ou absente → rejeté (400) ; événement sans le `organizationId` de confiance en métadonnée → accepté (200) mais ignoré, plutôt que deviné.
- La création de session Checkout (`POST /api/billing/checkout`) a été appelée avec une fausse clé — elle atteint bien l'API Stripe réelle et se fait rejeter proprement (401 de Stripe, propagé en erreur applicative), ce qui confirme que le code est correct jusqu'à la frontière de l'appel réseau, sans prouver qu'un vrai paiement aboutit.
- Restriction owner-only (ni manager, ni autre rôle) vérifiée sur les trois routes de facturation et sur `/dashboard/billing`.
- Sans aucune clé Stripe configurée, tout le reste de l'app continue de fonctionner normalement (`npm run setup` ne dépend pas d'un compte Stripe) — `/dashboard/billing` affiche un avertissement clair, les routes renvoient un 501 propre plutôt qu'un plantage.

**Ce qui n'a pas pu être vérifié** (pas d'identifiants Stripe disponibles dans cet environnement) : un vrai parcours de paiement de bout en bout — carte de test, redirection Checkout réelle, retour sur `success_url`, webhook réellement envoyé par Stripe plutôt que simulé. **À faire avant le premier restaurateur pilote payant**, avec un compte Stripe en mode test.

**Design** : un seul plan (~400 €/an, §8), pas de sélecteur de tarif. `organization_id` transite dans les métadonnées de la session Checkout et de l'abonnement Stripe créés par cette app elle-même ; le webhook, une fois la signature Stripe vérifiée, peut donc faire confiance à cette métadonnée et écrire via `withTenant()` normal — **aucune sixième fonction `SECURITY DEFINER` n'a été nécessaire**, contrairement à l'intuition initiale (le webhook n'a de session ni de compte, comme signup/login/QR, mais contrairement à eux il n'a pas besoin de *résoudre* un tenant depuis une donnée non fiable : il le relit depuis une donnée que l'app a écrite elle-même et que Stripe se contente de renvoyer). Bonne confirmation que le modèle en §12.3 tient sans multiplier les contournements.

### 12.8 Limitation de débit (durcissement post-Phase 0)

**Mécanisme** : compteur en mémoire, fenêtre fixe, par clé (`src/lib/rate-limit.ts`). Même limite de conception que le temps réel (§12.6) : un seul processus Node, pas de magasin partagé — un déploiement multi-instances appliquerait la limite séparément sur chaque instance, ce qui la multiplie de fait par le nombre d'instances plutôt que de la faire respecter globalement. À remplacer par un magasin partagé (Redis) si l'hébergement final est multi-instances ; à trancher avec le reste de l'hébergement (§12.4), pas avant.

**Où c'est appliqué, et pourquoi ces clés précises :**
- **Connexion** : par IP (10/15 min) *et* par email (5/15 min) — une seule source qui teste beaucoup de comptes est bloquée par la première, beaucoup de sources qui testent un seul compte sont bloquées par la seconde. Vérifié en conditions réelles au-delà de 5 tentatives sur un même email.
- **Inscription** : par IP (5/heure) — contre la création automatisée d'organisations bidon. Vérifié : la 6ᵉ tentative en une heure depuis la même IP est rejetée avec un `Retry-After` correct (~3600s).
- **Commande client** (`/menu/[qrToken]`) : par table (20/5 min) *et* par IP (30/heure) — la table protège contre un script qui spamme une seule table, l'IP contre un script qui teste plusieurs tables. Vérifié : exactement 20 commandes passent sur une même table, la 21ᵉ est rejetée.
- **Acceptation et lecture d'invitation** : par IP, limites larges (20–30/heure) — les jetons (32 octets aléatoires) rendent le brute-force impraticable de toute façon ; c'est une assurance bon marché contre le sondage automatisé, pas la vraie défense.
- **Invitation de staff** : par organisation (20/heure), pas par personne qui invite — ce qui est borné, c'est "combien de liens d'invitation ce restaurant peut générer par heure", pas l'activité d'un individu.
- **Facturation** (Checkout, Portail) : par organisation, limites larges — même logique que les invitations, protection de dernier recours plutôt que contrainte pensée pour l'usage normal.

**Ce qui n'est délibérément pas limité** : les lectures authentifiées du tableau de bord (`/api/orders`, `/api/menu/*`, `/api/staff`) — un membre du staff qui recharge sa page ne doit jamais se heurter à une limite pensée pour du trafic public non authentifié.

### 12.11 Deuxième passage design : système de tokens, Framer Motion, dashboard en dark mode (27 juillet 2026)

Le fondateur a fourni un brief de design system complet (palette, typographie, composants, animations précises) accompagné d'une capture d'écran de référence, avec la consigne explicite de commencer par un fichier de tokens et de l'appliquer partout. Les composants qui ont besoin d'une valeur en dehors de ce que les classes Tailwind expriment (dégradés inline, variants Framer Motion) importent le même fichier. **Deux thèmes, pas un seul avec un interrupteur.** Consigne explicite : le site (landing, auth, menu public) reste clair, seul le dashboard restaurant passe en dark mode (`#0F1420` / cartes `#1A2035`). **Mockup héro flottant vs captures d'écran réelles — deux mécanismes différents, délibérément.** Le héro (`src/components/hero-mockup.tsx`) est une illustration stylisée dessinée en JSX/Tailwind (téléphone incliné, cartes de notification qui flottent à des vitesses différentes via des classes `animate-float*` distinctes) — pas une vraie capture, parce que l'effet demandé (inclinaison, flottement, cartes détachées superposées) ne fonctionne pas avec une capture d'écran rectangulaire réelle. Les deux répondent à des besoins différents : le héro vend une sensation, l'aperçu prouve que c'est vrai — mentionné explicitement en commentaire dans `hero-mockup.tsx` pour que ça ne soit pas "corrigé" par erreur plus tard en remplaçant l'un par l'autre.

Construire un vrai toggle à trois tarifs aurait donc soit contredit cette décision business, soit affiché un faux prix "économisé" sans référence réelle à comparer. Prêt à être branché dès que de vrais avis existent, sans travail de design supplémentaire à ce moment-là.

Demande de suite du fondateur, plus ouverte : "ajouter des design animés et mettre le site plus beau avec ui ux". ### 12.18 Vague de fonctionnalités « growth » : OAuth, vérification email, modes de commande, analytics, traduction, paiement client, photos IA (30 juillet 2026)

Demande du fondateur : des captures d'un concurrent (MenuForma) montrant un ensemble bien plus large de fonctionnalités, plus la connexion Google/Apple et la vérification d'email nommées explicitement. Vu l'ampleur (multi-QR, paiement client, images IA, multilingue automatique, analytics, comptes multi-restaurant, impression de reçus...), une question de priorisation a été posée avant de commencer plutôt que de deviner — le fondateur a choisi les quatre groupes proposés en plus de l'authentification : QR/commande étendus, analytics, traduction automatique, paiement client + photos IA. Récapitulatif ci-dessous, une seule migration Postgres (`20260730000000_growth_features`, plus deux correctifs le même jour) pour l'ensemble des nouvelles tables/colonnes.

**Connexion Google + Apple** (`src/lib/oauth.ts`, `/api/auth/{google,apple}/{start,callback}`). Flux OAuth 2.0 authorization-code standard pour Google ; pour Apple, `response_mode=form_post` (callback en vrai POST cross-site, pas une redirection) et un client "secret" qui est en réalité un JWT ES256 signé à la volée avec la clé privée téléchargée une fois sur le portail développeur Apple (`jose`, déjà une dépendance pour les sessions). Une seule fonction `SECURITY DEFINER`, `oauth_authenticate()`, couvre les trois issues possibles atomiquement : identité déjà liée → connexion directe ; email déjà utilisé par un compte mot de passe existant → liaison du compte (un propriétaire qui s'était inscrit au mot de passe peut ensuite cliquer "Continuer avec Google" sur ce même email) ; email inconnu → création d'une organisation + d'un propriétaire, exactement comme `create_organization_and_owner()`, puis liaison. Conséquence sur le schéma : `users.password_hash` devient nullable (un compte 100 % OAuth n'en a jamais) — `login` rejette explicitement toute tentative de mot de passe sur un `password_hash` nul plutôt que de risquer un appel bcrypt sur `null`. Limite assumée et documentée en commentaire : l'inscription OAuth ne collecte pas le nom du restaurant (aucun formulaire intermédiaire construit pour ça, vu l'ampleur déjà engagée) — le nom d'organisation part sur un placeholder ("Restaurant de {nom}"), à renommer plus tard une fois qu'un champ d'édition existera. Ni Google ni Apple n'ont pu être exercés contre une vraie inscription d'app dans cet environnement — vérifié à la place par le chemin de repli réel : bouton toujours affiché (même logique que le bouton Stripe de `/dashboard/billing` qui s'affiche toujours et s'explique si non configuré), clic sans clé → retour sur la page avec un message "indisponible sur cet environnement" au lieu d'un crash.

**Vérification d'email** (`src/lib/verification.ts`, `/api/auth/verify-email`, `/api/auth/resend-verification`). Token à usage unique (24 h), envoyé via l'infrastructure email existante (§12.16) à l'inscription par mot de passe ; les comptes OAuth sont considérés vérifiés d'office (Google/Apple garantissent déjà l'email) et un compte invité qui clique son lien d'invitation l'est aussi désormais (`accept_invitation()` mis à jour pour poser `email_verified_at` — cliquer un lien envoyé par email est déjà la preuve qu'on cherchait, inutile de la redemander juste après). Bannière `src/components/email-verification-banner.tsx` sur tout le dashboard, relit `/api/me` plutôt que de faire confiance au JWT de session (qui ne porte pas ce champ et serait de toute façon périmé dès la vérification) — c'est un rappel, pas une porte : aucune fonctionnalité n'est bloquée pour un compte non vérifié aujourd'hui.

**Modes de commande étendus** (`RestaurantTable.orderingMode` : `TABLE`/`COUNTER`/`PICKUP`/`DISPLAY_ONLY`). Choix d'architecture qui simplifie beaucoup par rapport au plan initial : plutôt que d'inventer un nouveau type d'entité pour "QR comptoir" ou "lien de retrait", ce sont toujours des lignes `tables` ordinaires — une "table" ici veut dire "un point d'entrée de commande avec son propre QR", pas nécessairement un meuble. `Order.orderingMode` capture une *photo* du mode au moment de la commande (pas une jointure vivante), pour que l'historique reste exact même si le lien est reconfiguré plus tard. `Order.orderNumber` est une colonne `SERIAL`, globale (pas par organisation) — un ticket #47 peut suivre un #12 d'un autre restaurant sans que ça pose de problème, chaque dashboard ne voit que ses propres commandes de toute façon. `DISPLAY_ONLY` retire entièrement le panier côté client (aucun bouton "+"), `PICKUP` demande un nom avant de valider (nouveau champ `Order.pickupName`), `COUNTER` affiche le numéro de commande à la place d'un nom de table. Page `/dashboard/tables` réutilisée telle quelle (mêmes cartes, un sélecteur de mode en plus) plutôt qu'une nouvelle page — ce sont conceptuellement les mêmes "liens de commande".

**Analytics** (`/dashboard/analytics`, `GET /api/analytics`, nouvelle table `menu_views`). Vues du menu comptées à chaque chargement de `/api/public/menu/[qrToken]` — une écriture RLS ordinaire dans la même transaction `withTenant` que la lecture du menu, pas une fonction `SECURITY DEFINER` de plus : `resolveTableByQrToken` a déjà produit l'`organizationId` à ce stade. Trois graphiques en barres verticales/horizontales construits à la main en CSS/SVG (pas de bibliothèque de graphes ajoutée pour trois vues simples) — le premier jet avait un bug réel : `items-end` sur le conteneur flex empêchait les colonnes filles de s'étirer sur toute la hauteur, donc chaque barre calculait sa hauteur en pourcentage d'un parent haut de 0px et restait invisible ; corrigé en donnant une hauteur en pixels explicite au "rail" de chaque barre plutôt qu'en `h-full` hérité. KPIs (vues, commandes, chiffre d'affaires) sur 14 jours, plats populaires sur 30 jours — agrégation faite en JavaScript après une lecture Prisma classique plutôt qu'en SQL brut avec `date_trunc`, volume de données d'un seul restaurant largement assez petit pour ça, et ça évite d'introduire une nouvelle requête `$queryRaw` dans une route qui n'en avait pas besoin.

**Traduction automatique du menu** (`src/lib/translate.ts`, DeepL, `POST /api/menu/translate`, nouvelle table `menu_item_translations`). Quatre langues (FR/DE/ES/PT), pas "70+" : le palier gratuit de DeepL couvre une trentaine de langues et rien dans cette passe n'a jamais réellement traduit vers plus que ces quatre — annoncer un chiffre jamais atteint aurait été le même genre de survente que le reste de CONTEXT.md essaie d'éviter. Seuls les plats sont traduits (nom + description) ; les catégories restent bilingues IT/EN comme avant (`nameIt`/`nameEn`), coupure de scope assumée — bug réel trouvé et corrigé pendant la vérification : le rendu public retombait sur `category.nameEn` pour *toute* langue différente de l'italien, y compris FR/DE/ES/PT, montrant "Starters"/"First courses" en anglais alors que le reste de la page était en français ; corrigé pour ne retomber sur l'anglais que si la langue choisie est explicitement "en", et sur l'italien pour toute autre langue. Chaque plat manquant une traduction (ajouté après la dernière traduction, par exemple) retombe silencieusement sur l'italien plutôt que d'afficher un trou. Deuxième bug réel trouvé en testant à 6 langues sur mobile (IT/EN + 4) : l'en-tête du menu public se comprimait sur trois lignes, le nom du restaurant coupé au milieu d'un mot — corrigé en faisant passer les pastilles de langue sur une deuxième ligne, défilable horizontalement, dès qu'au moins une langue supplémentaire existe (le cas courant, sans traduction, garde la mise en page à une ligne inchangée).

**Paiement client en ligne** (`POST /api/public/orders/[qrToken]/[orderId]/pay`, `Order.paymentStatus`/`stripeCheckoutSessionId`). Simplification délibérée et documentée en commentaire dans le code : ce paiement passe par le même compte Stripe que l'abonnement du restaurateur (§12.7), pas par un compte Stripe Connect séparé par organisation — l'argent collecté atterrit donc sur le solde de la PLATEFORME, pas sur celui du restaurant. Correct pour cette passe (jamais testé contre un vrai compte de toute façon) mais un vrai lancement a besoin de Stripe Connect pour que chaque organisation encaisse ses propres commandes ; noté explicitement ci-dessous pour ne pas être découvert en production. Distingué du webhook de facturation existant par `session.mode === "payment"` plutôt que par la présence de tel ou tel champ. Le "Payer en ligne" n'apparaît que si `getStripeClient()` renvoie un client réel (`onlinePaymentAvailable` dans la réponse de `GET /api/public/menu/[qrToken]`) — jamais un bouton mort ; payer sur place reste le chemin par défaut et fonctionne exactement comme avant.

**Photos de plats générées par IA** (`src/lib/ai-image.ts`, OpenAI Images, `POST /api/menu/generate-photo`). Nécessite à la fois `OPENAI_API_KEY` *et* le stockage S3 déjà configuré (§12.16) — l'image générée doit être persistée quelque part de permanent, que l'API réponde en base64 ou par une URL qui expire au bout d'environ une heure côté OpenAI ; jamais stockée telle quelle comme `photoUrl`, toujours réuploadée dans le bucket de l'app. Réutilise `uploadImage()` (`folder: "menu-items"`, même chemin que l'upload manuel et l'import de fichier) plutôt que d'inventer un nouveau mécanisme de stockage. Bouton "ou générer avec l'IA" à côté de "ou importer une photo" dans `item-form.tsx`, fonctionne aussi bien à la création (pas encore d'id) qu'à l'édition, sur le même principe que l'upload manuel (§12.16).

**Bug d'infrastructure réel, trouvé en testant vraiment une commande retrait de bout en bout** (pas seulement en lisant le code) : la colonne `Order.orderNumber` (`SERIAL`) échouait en production avec `permission denied for sequence orders_order_number_seq`. Cause : `ALTER DEFAULT PRIVILEGES ... GRANT ... ON TABLES TO app_user` (`docker/init-roles.sql`, depuis la toute première migration RLS) ne couvre que les tables, jamais les séquences qu'une colonne `SERIAL`/identité crée implicitement — `app_user` pouvait insérer dans `orders` mais pas appeler `nextval()` sur sa propre séquence d'auto-incrément. Corrigé à deux niveaux : `docker/init-roles.sql` reçoit une ligne `ON SEQUENCES` équivalente pour que toute base fraîchement provisionnée soit couverte d'emblée, et une migration de rattrapage (`20260730000200_fix_order_number_sequence_grant`) accorde la même permission sur la base déjà existante. Un rappel que "`tsc`/`eslint` au vert" ne suffit jamais à garantir qu'un chemin serveur fonctionne réellement — seul un vrai POST contre une vraie base l'a révélé.

Vérifié pour l'ensemble : `tsc`, `eslint`, `vitest` (16 tests) et `next build` au vert ; chaque flux exercé en vrai via Playwright contre l'app qui tourne (création des trois nouveaux types de lien, commande retrait complète bout en bout avec numéro de ticket affiché, panneau de traduction avec dégradation propre, bouton IA avec dégradation propre, bannière de vérification email, page analytics avec vraies données du jeu de démo) plutôt que simplement lu dans le code — c'est cette vérification qui a trouvé les quatre bugs réels listés ci-dessus (barres à hauteur nulle, catégories mal repliées sur l'anglais, en-tête comprimé à 6 langues, séquence sans permission), aucun visible en relisant le diff.

### 12.19 Application mobile Android + iOS (Expo/React Native), parité complète avec le dashboard (30 juillet 2026)

Demande du fondateur : une app Android et une app iOS pour que le serveur et toute l'équipe reçoivent les notifications, et que le propriétaire puisse gérer l'application. Avant de commencer, deux limites techniques annoncées explicitement, pas glissées en cours de route : aucune compilation/test réel possible pour iOS dans cet environnement (pas de macOS/Xcode — code écrit et câblé, jamais compilé pour de vrai) ; la livraison réelle de notifications push nécessite des identifiants Apple Developer/Firebase absents ici, donc le mécanisme est câblé et vérifié dans sa mécanique, jamais contre une vraie livraison. Question de périmètre posée ensuite (MVP commandes+notifications, parité complète, ou encore plus réduit) — le fondateur a choisi **la parité complète avec le dashboard web** : commandes/notifications, équipe, menu, tables/QR, analytics, marque, abonnement, pas seulement le socle minimal.

**Une seule base de code, deux plateformes.** `mobile/` (Expo Router, TypeScript) à la racine du repo, un React Native/Expo qui produit Android et iOS depuis le même code — pas deux apps natives séparées. Appelle exactement la même API Next.js existante (`src/app/api/**`), aucun backend mobile distinct : une nouvelle route côté web n'a besoin d'aucun travail supplémentaire pour être immédiatement appelable depuis le mobile, même chemin, même forme de réponse.

**Authentification par bearer token, pas par cookie.** Le fetch de React Native n'a pas de pot à cookies comme un navigateur, donc la session cookie httpOnly existante (`src/lib/session.ts`) ne marche pas telle quelle. Changement minimal côté serveur, à fort effet de levier : `getSession()` vérifie désormais l'en-tête `Authorization: Bearer <token>` avant de retomber sur le cookie ; les trois routes qui délivrent une session (`/api/auth/login`, `/api/auth/signup`, `/api/invitations/accept`) renvoient maintenant aussi le JWT signé brut dans le corps JSON, en plus de continuer à poser le cookie pour le client web. Résultat vérifié par un aller-retour `curl` réel (pas de lecture de code) : les ~30 routes `requireSession()` existantes fonctionnent pour le mobile sans qu'aucune n'ait été touchée individuellement. Stockage du token sur l'appareil via `expo-secure-store` (Keychain/Keystore) — sa version web, utilisée uniquement pour la prévisualisation locale dans cet environnement, s'est révélée cassée (`getValueWithKeyAsync is not a function`, vraie erreur trouvée en testant, pas en lisant le code) ; contournée par un repli `localStorage` derrière `Platform.OS === "web"`, sans conséquence sur iOS/Android réels qui utilisent toujours l'implémentation native.

**Notifications push** (`push_tokens`, migration `20260730010000_push_tokens`, mêmes RLS/`tenant_isolation` que toute autre table du projet). `POST/DELETE /api/push-tokens` enregistre/retire le token Expo de l'utilisateur courant (upsert sur `token` seul, pas par utilisateur — une reconnexion sous un autre compte sur un appareil partagé réassigne correctement l'appareil). `src/lib/push.ts` envoie via l'endpoint HTTP public d'Expo (`exp.host/--/api/v2/push/send`, aucune clé requise pour l'appel lui-même). Déclenché en tâche de fond (`.then(...).catch(console.error)`, après la transaction principale et la construction de la réponse) sur deux événements : nouvelle commande (`/api/public/orders/[qrToken]`) et appel serveur (`/api/public/staff-calls/[qrToken]`) — un échec Expo ne peut jamais transformer une commande réussie en réponse en échec. Réellement vérifié : écriture en base confirmée, appel HTTP réel vers l'endpoint Expo confirmé sans erreur. Ce qui ne peut pas être vérifié ici, documenté comme tel plutôt que présumé acquis : la réception réelle sur un appareil, qui nécessite un identifiant de projet EAS réel — `registerForPushNotifications()` échoue silencieusement (`console.warn`) sans jamais faire planter la connexion si ce n'est pas configuré, même discipline de dégradation propre que Stripe/email/S3/OAuth/DeepL/OpenAI dans ce document.

**Écrans construits, parité complète :** connexion, `Commandes` (plateau de commandes en direct par sondage 4s + rafraîchissement immédiat sur réception d'une notification push, bannière "appel serveur", actions d'avancement de statut — pas de SSE, `EventSource` natif n'existe pas dans React Native), `Analytics` (KPIs + graphiques en barres reconstruits en `View`/`StyleSheet`, même agrégation que la route existante), `Profil` (déconnexion avec désenregistrement du token push), et un onglet `Gérer` (visible seulement propriétaire/manager) menant vers `Équipe` (liste, invitation, activation/désactivation), `Menu` (catégories, plats, allergènes, photo via `expo-image-picker`), `Tables/QR` (CRUD, QR généré nativement via `react-native-qrcode-svg`, partage du lien via `Share`), `Marque` (upload logo/fond) et `Abonnement` (propriétaire seul, ouvre Stripe Checkout/Portal dans le navigateur de l'appareil via `Linking.openURL`, jamais de paiement intégré dans l'app). Quatre onglets seulement, pas sept-huit à plat : sur un petit écran, les écrans réservés à la gestion vivent derrière un onglet "hub" plutôt que d'encombrer la barre.

**Nouvelle route backend, seule vraie addition d'API pour cette passe** : `GET /api/billing` (réservée au propriétaire). La page web de facturation lit directement la base dans un composant serveur ; le mobile n'a pas d'équivalent, donc cette route existe pour exposer `subscriptionStatus`/`trialEndsAt`/si Stripe est configuré en JSON. Vérifiée par un aller-retour `curl` réel avec un token de session valide.

**Écart de typographie assumé.** Les polices exactes du web (Big Shoulders Display/Manrope/JetBrains Mono) n'ont pas pu être installées : `@expo-google-fonts/*` entre en conflit de dépendances (`ERESOLVE`) avec les dépendances web-only d'`expo-router` (`vaul`→`@radix-ui/*`), sans rapport avec les polices elles-mêmes. Pas forcé avec `--legacy-peer-deps` pour un simple remplacement de police ; `mobile/src/lib/theme.ts` utilise des polices système en approximation (`fontWeight: "800"` pour les titres, `Courier` pour le monospace), documenté en commentaire dans le code — même hex de couleurs et rayons que le web, typographie exacte à reprendre une fois ce conflit résolu en amont.

**Bug réel trouvé en construisant, pas en lisant le code : le `tsconfig.json` racine typait aussi `mobile/`.** Son `include: ["**/*.ts", "**/*.tsx", ...]` n'excluait que `node_modules`/`web scarping`, pas `mobile/` — une fois le dossier `mobile/` apparu, `npm run typecheck` à la racine s'est mis à résoudre les fichiers `mobile/src/**` contre les types React 19 de `mobile/node_modules`, entrant en collision avec les types React 18 du projet Next.js (erreurs `TS2786` en cascade, composants React Native "not a valid JSX element type") — deux projets TypeScript distincts qui n'auraient jamais dû se voir. Corrigé en ajoutant `"mobile"` à l'`exclude` du `tsconfig.json` racine ; `mobile/` garde son propre `tsconfig.json` indépendant.

Vérifié : `tsc --noEmit` propre dans les deux projets séparément, export Metro web (`expo export --platform web`, technique de test local uniquement, jamais une cible livrée) sans erreur sur les 12 écrans, `next build`/`vitest` (16 tests) toujours au vert côté racine après les changements d'auth/push/`/api/billing`, écran de connexion vérifié visuellement par Playwright avec le rendu réel de la direction Comanda. Un blocage CORS est apparu en testant la connexion depuis l'export web servi sur un port différent (8090) que l'API (3000) — attendu et sans rapport avec une vraie app : le `fetch` natif d'iOS/Android n'a pas de politique de même origine, ce blocage n'existe que dans ce test de prévisualisation navigateur, jamais sur un vrai appareil.

### 12.21 Nouvelle direction visuelle « Liquid Glass », remplace « Comanda » (2 août 2026)

Demande du fondateur : améliorer le design « comme un iPhone 17 Pro ». Question de clarification posée avant de commencer, vu l'ampleur potentielle (juste des effets de verre sur le mobile ? toute l'app ? juste la landing ?) — le fondateur a choisi explicitement la **refonte complète, web ET mobile**, en abandonnant la direction « Comanda » (ticket de cuisine, §12.17) construite sur plusieurs passages précédents. Décision assumée : remplacer, pas superposer.

**Ce que « façon Apple » veut dire ici** : le matériau logiciel actuel d'Apple (ère iOS 26 / iPhone 17 Pro), pas l'esthétique matérielle du téléphone lui-même — surfaces translucides avec flou d'arrière-plan (« Liquid Glass »), coins très arrondis façon continuous corner, élévation par ombres douces et diffuses plutôt que des ombres portées dures, une seule police système à graisse variable plutôt qu'un mélange de polices display/mono. L'accent marigold de la marque (`brand`, #E2811F) est conservé tel quel — changer de matériau visuel n'est pas la même chose que renoncer à l'identité de marque construite depuis des mois (logo, marketing) ; « façon Apple » décrit le *traitement*, pas une bascule vers le bleu système d'Apple.

**Le point de levier architectural déjà en place a été exploité plutôt que réécrire chaque page.** Le système précédent (§12.14, §12.17) centralise déjà tout dans `src/lib/design-tokens.ts` → `tailwind.config.ts` → les classes partagées de `globals.css` (`.card`, `.card-dash`, `.btn-primary`, `.badge-pill`, `.ticket`, etc.), que chaque page consomme sans répéter de styles Tailwind bruts. Réécrire ces trois fichiers a suffi à faire cascader le nouveau matériau sur la quasi-totalité du web (landing, dashboard, menu public, auth) sans toucher individuellement aux ~25 fichiers de page.

**Couleurs** (`design-tokens.ts`) : `ink`/`paper` deviennent les couleurs texte/fond réelles d'apple.com (#1D1D1F / #F5F5F7), `muted` devient le gris "secondary label" d'Apple (#6E6E73). Les trois couleurs de statut (`progress`/`ready`, `brand` doublant "à faire") sont remappées sur les couleurs système iOS (`systemBlue` #0A84FF, `systemGreen` #30D158) plutôt que le denim/mousse de la direction précédente — même discipline "exactement trois couleurs, jamais décoratives" qu'avant, juste rehuée pour lire "natif" du nouveau matériau. `dashBg` passe du slate sombre (#14181E) au noir vrai (#000000, esprit OLED "Space Black") : le tableau de bord reste sa propre pièce toujours sombre (pas un bascule clair/sombre, décision inchangée depuis §12.14), mais devient le fond sur lequel les cartes en verre flottent plutôt qu'un simple fond opaque. Quatre nouveaux tokens `glassLight`/`glassLightBorder`/`glassDark`/`glassDarkBorder` (blancs translucides à faible opacité) : les remplissages des cartes ne sont plus des couleurs pleines, ils sont pensés pour être posés sur `backdrop-blur`.

**Typographie : une seule police système, pas un remplacement de police.** `-apple-system, BlinkMacSystemFont, "SF Pro Text/Display"` en tête de chaque pile `font-*` dans `tailwind.config.ts` — sur du vrai matériel Apple, ça rend littéralement San Francisco, exactement la façon dont apple.com définit ses propres polices. Manrope reste chargé (aucune nouvelle dépendance) mais seulement comme repli multiplateforme, plus comme police display distincte. Big Shoulders Display et JetBrains Mono (les deux Google Fonts de la direction « Comanda ») retirés de `layout.tsx`. Point clé d'efficacité : `font-display` et `font-mono` gardent leurs noms de classe (utilisés dans ~70 emplacements à travers l'app) mais résolvent désormais vers la même pile système — San Francisco se différencie par graisse/taille optique, pas par famille, donc aucune des ~70 occurrences n'a dû être touchée individuellement pour adopter le nouveau système. `.font-mono` reçoit une petite règle CSS (`font-variant-numeric: tabular-nums`) pour retrouver l'alignement en colonnes des prix/horodatages que la police à chasse fixe fournissait, sur la police système plutôt que sur une police à chasse fixe — exactement ce que fait SF Pro elle-même avec ses chiffres tabulaires.

**Rayons et ombres** : `radius.card` passe de 6px à 22px, `radius.container` de 10px à 32px — des coins généreux façon iOS (cartes/feuilles autour de 20-32px), un vrai changement de posture par rapport aux rayons serrés inspirés du ticket de cuisine. Les ombres (`shadow.soft`/`softLg`) deviennent nettement plus douces et diffuses, à opacité réduite — le flou du matériau en verre fait l'essentiel du travail de "flottaison", l'ombre n'est plus qu'un appui à faible opacité.

**Motif du ticket perforé, retiré.** Le motif signature de la direction « Comanda » (`::before` en dégradé radial simulant le bord déchiré) est supprimé de `.ticket`/`.ticket-dash` dans `globals.css` — ces classes restent comme des alias (`@apply card`/`@apply card-dash`) précisément pour ne pas avoir à traquer chaque appelant existant (le tableau de commandes, la carte de commande en direct du hero, les cartes flottantes) : ils gardent leur nom de classe, changent de matériau sans changement de code. Même logique pour `.badge-pill`, qui passe d'un badge tamponné/rectangulaire en monospace à une capsule (`rounded-full`) en verre teinté façon badge iOS, et pour `.eyebrow`, qui perd sa rotation "tampon encreur" pour devenir une pilule de verre propre. `.bg-dot-grid` (texture de points) devient un halo de couleur radial doux et flou, `.bg-rail-top` (ligne pointillée) devient un simple filet 1px — les deux anciens motifs référençaient trop explicitement l'imprimé/le ticket pour survivre au changement de direction.

**Nettoyage du code mort retiré avec le motif qu'il servait** : `stampRotations` (rotations aléatoires pour badges tamponnés) et le keyframe/l'animation `stamp` (le settle rotation+scale façon tampon) — vérifiés comme non référencés ailleurs dans le code avant suppression, code mort qui appartenait explicitement à la direction abandonnée.

**Mobile : même jeu de tokens, effet de verre réel via `expo-blur`.** `mobile/src/lib/theme.ts` reprend exactement les mêmes valeurs hex que le web. Contrairement au web (où `backdrop-blur` est du CSS), React Native n'a pas de flou d'arrière-plan natif au niveau du style — `expo-blur` (déjà listé dans les dépendances compatibles Expo SDK 57, aucun conflit de peer-deps comme celui rencontré pour les polices en §12.19) fournit un vrai composant `BlurView`. `Card`/`TicketCard` dans `mobile/src/components/ui.tsx` sont désormais un seul composant construit sur `BlurView` (`tint="dark"`, l'app mobile vivant entièrement sur le fond toujours sombre) — un vrai flou d'arrière-plan sur iOS/Android, pas juste une couleur translucide approximant l'effet. `TicketCard` reste un alias de `Card`, même raisonnement de compatibilité des call-sites que côté web. `radius.card` passe de 6 à 22, badges deviennent des capsules `rounded-full`, mêmes couleurs système iOS que le web.

**Vérifié** : `tsc --noEmit` propre (racine et `mobile/`), `eslint .` propre, `next build`/`vitest` (16 tests) au vert, export Metro web sans erreur (`BlurView` ne plante pas sur sa dégradation web). Capture Playwright de la landing (héro, mockup produit, carte de connexion), du tableau de bord (verre sombre sur noir vrai), du menu public (verre clair sur fond clair), et de quatre écrans mobiles (connexion, commandes, hub gérer, profil) — comparés visuellement à la référence Apple/iOS visée par le fondateur.

**Écart honnête, pas caché** : San Francisco n'est réellement rendue que sur le matériel Apple (iOS Safari/WebKit, et nativement dans l'app mobile) — sur Windows/Android/Linux, la pile `-apple-system` retombe sur Manrope (web) ou Roboto (mobile Android, via la police "System" native), jamais sur une vraie police Apple téléchargée : c'est le même compromis que le propre site apple.com fait pour ses visiteurs non-Apple, pas une limite spécifique à cette implémentation.

### 12.23 Premier déploiement Railway : correction de l'origine derrière le proxy inverse (2 août 2026)

Premier vrai déploiement sur Railway (`loving-solace`, service Web-Scarping + Postgres géré). Après avoir corrigé le rôle Postgres (`app_migrator`) et le suivi de branche (`main` était 26+ commits derrière `claude/new-session-hio1f5`, fusionné), le bouton "Continuer avec Google" échouait en production avec `redirect_uri_mismatch`, la `redirect_uri` envoyée pointant vers `https://localhost:8080/...` au lieu du vrai domaine public.

Cause : `req.nextUrl.origin`/`new URL(req.url).origin`, utilisés partout où l'app construit une URL absolue, reflètent l'adresse de liaison interne du conteneur derrière le proxy inverse de Railway (qui termine le TLS et transmet en HTTP simple), pas le domaine public — même mécanisme que celui déjà connu pour `x-forwarded-for`/`getClientIp` (§12.8), jamais appliqué à l'origine elle-même jusqu'ici. Corrigé une fois, centralement : `getRequestOrigin(req)` (`src/lib/rate-limit.ts`, à côté de `getClientIp` pour la même raison — faire confiance aux en-têtes `x-forwarded-proto`/`x-forwarded-host` posés par le proxy plutôt qu'à la requête brute), puis chaque site remplacé (`middleware.ts`, les quatre routes OAuth, `verify-email`, `signup`, `resend-verification`, `staff/invite`, `billing/checkout`, `billing/portal`, le paiement client public).

Vérifié : `tsc`/`eslint`/`vitest` au vert. Pas encore re-testé contre un vrai clic Google en production au moment d'écrire cette entrée — à confirmer au prochain déploiement.

### 12.30 Sélecteur de langue du site (FR/IT/EN/ES/DE/AR), architecture i18n (3 août 2026)

Demande explicite : une icône pour changer la langue de l'interface (FR/IT/EN/ES/DE/AR). À distinguer d'emblée d'une fonctionnalité existante sans rapport : le menu public (`/menu/[qrToken]`) a son propre sélecteur IT/EN + langues additionnelles (FR/DE/ES/PT), mais celui-là traduit le **contenu du menu** d'un restaurant donné (noms/descriptions de plats, via DeepL, `src/lib/translate.ts`) -- ce chantier-ci traduit le **chrome de l'application elle-même** (nav, boutons, titres), un système entièrement différent bien que les deux se croisent sur `/menu/[qrToken]` (voir plus bas).

**Architecture** (`src/lib/i18n/`) : `languages.ts` définit les six langues + un flag `rtl` (uniquement l'arabe). Le choix du visiteur est stocké dans un cookie (`mbqr_locale`, 1 an) posé par une Server Action (`set-locale-action.ts`). Deux façons de le lire selon le type de composant :
- **Composants serveur** (la landing, `/prezzi`, `/chi-siamo`, le layout du dashboard) : `get-locale.ts` lit le cookie via `next/headers` à chaque requête -- pas de JS client nécessaire, la page entière se re-rend déjà dans la bonne langue au premier rendu serveur.
- **Pages entièrement client** (`/login`, `/signup`, `/invite/[token]`, qui n'ont aucun parent serveur au-dessus d'elles) : `use-locale.ts` (`useLocale()`) lit le cookie côté client, avec le même schéma SSR-safe en deux temps que `useSafeReducedMotion` (§12.11) -- valeur par défaut au montage, vraie valeur appliquée dans un `useEffect`. Un bug intermédiaire a été trouvé et corrigé ici : `router.refresh()` (déclenché par le sélecteur après avoir posé le cookie) ne re-rend que les composants serveur -- sur une page 100% client, ça ne fait rien du tout, donc changer de langue restait sans effet visuel sur `/login`/`/signup`/`/invite`. Corrigé en ajoutant un `CustomEvent` (`mbqr-locale-change`) émis par `LanguageSwitcher` au moment du clic, écouté par `useLocale()` -- effet immédiat, sans dépendre du re-rendu serveur.

`src/components/language-switcher.tsx` : icône globe + code langue (ex. « FR ») ouvrant un menu déroulant avec les six langues dans leur nom natif, coché sur la langue active -- présent dans la nav de la landing (desktop + tiroir mobile), sur les trois pages d'authentification (`AuthShell`), et dans la barre latérale du dashboard (variante sombre, prop `variant="dark"`).

**RTL pour l'arabe** : `<main dir={...}>` sur la landing, `<main dir={...}>` dans `AuthShell`, `<div dir={...}>` sur le conteneur racine du dashboard -- calculé depuis `isRtl(locale)`. Confirmé par capture Playwright que la mise en page se réoriente correctement (nav, grille du hero, alignement du texte) sans changement CSS supplémentaire : le site utilise déjà flexbox/grid avec des classes Tailwind qui résolvent leurs propriétés selon la direction du document (comportement natif de la spec CSS, pas un ajout de ce chantier) -- seuls les éléments positionnés en absolu avec des offsets physiques (`-right-`, `-left-`, les cartes flottantes décoratives de `HeroMockup`) ne se retournent pas, jugé cosmétique et laissé tel quel.

**Ce qui est traduit dans les six langues, vérifié par capture Playwright dans chacune** :
- La landing complète (`src/app/page.tsx` + `landing-nav.tsx` + `landing-footer.tsx` + `pricing-toggle.tsx` + `product-preview.tsx`) -- dictionnaire `src/lib/i18n/dictionaries/landing.ts`, une seule grosse interface `LandingDict` typée pour que TypeScript signale toute langue à qui il manquerait une clé.
- Les trois pages d'authentification (`login`/`signup`/`invite/[token]`) + `AuthShell`/`OAuthButtons` -- dictionnaire `dictionaries/auth.ts`, `roles` (Propriétaire/Manager/Serveur/Cuisine) partagé entre la page d'invitation et la barre latérale du dashboard.
- La coquille du dashboard (`dashboard/layout.tsx`) : libellés de nav (Commandes/Analytics/Staff/Menu/Tables/Marque/Abonnement), libellé de rôle, bouton de déconnexion -- dictionnaire `dictionaries/dashboard-shell.ts`.
- Le chrome du menu public (`/menu/[qrToken]`) pour les quatre langues DeepL existantes (FR/DE/ES/PT) : avant ce chantier, choisir une traduction de contenu dans une de ces langues laissait les boutons/le panier/la confirmation en anglais (`const t = lang === "it" ? T.it : T.en`) -- corrigé en ajoutant `T.fr`/`T.de`/`T.es`/`T.pt` et un vrai lookup `T[lang] ?? T.en`.

**Explicitement pas fait, et pourquoi** :
- **Les pages internes du dashboard** (éditeur de menu, tableau de commandes, tables, staff, facturation, marque, analytics) restent en français. Traduire fidèlement des centaines de libellés, en-têtes de tableau, messages de formulaire et d'erreur sur sept pages, dans six langues, est un chantier de taille comparable à tout ce qui précède -- tenté dans la même passe, le risque de qualité (traductions approximatives jamais relues, incohérences) dépassait la valeur d'un « tout ou rien » précipité. Vérifié : `tsc`/`eslint`/`vitest`/`next build` au vert ; changement de langue testé par Playwright sur la landing (IT→EN→AR, cookie posé, re-rendu serveur confirmé, `dir="rtl"` effectif), sur `/login`/`/signup` (bug du `router.refresh()` sur page 100% client trouvé et corrigé pendant cette même vérification), et sur le dashboard connecté (FR→DE, nav traduite, contenu de page toujours en français comme attendu et documenté ci-dessus).

**Logo web** (`src/components/logo.tsx`, `src/app/icon.svg`) : recoloré plutôt que remplacé par une image -- la structure "finder pattern" SVG existante (trois coins en motif QR imbriqué + un carré plein au quatrième coin) est conservée telle quelle pour rester nette à toute taille (nav, favicon, footer sombre), mais recolorée avec les teintes exactes échantillonnées dans les PNG fournis (`#274D3B`→`#1D3A2D` pour le dégradé de fond, `#D8AC5C` pour l'or des motifs) plutôt que devinées. Le wordmark texte devient "Tavolino".

**Icônes mobiles** (`mobile/assets/`) : contrairement au logo web, ces fichiers étaient encore les placeholders par défaut d'Expo (flèche bleue générique, jamais personnalisés) -- remplacés directement par `tavolino-app-icon-dark.png` fourni (redimensionné en 1024×1024 pour `icon.png`, 48×48 pour `favicon.png`, 512×512 pour `android-icon-foreground.png` ; `android-icon-background.png` recréé en aplat uni `#1D3A2D` assorti). `android-icon-monochrome.png` reste le défaut Expo -- aucun asset fourni ne permet d'en dériver un correctement, et comme le reste du build Android (jamais testé sur un vrai appareil, voir `mobile/README.md`) ce n'est pas vérifiable ici. L'écran de connexion mobile (`mobile/app/login.tsx`) affichait un rond de couleur avec la lettre "M" en guise de logo ; remplacé par l'image `icon.png` désormais réelle plutôt que gardé comme texte. `colors.brand` (orange, `mobile/src/lib/theme.ts`) n'a pas été touché : c'est la couleur d'accent de tout le thème sombre "Comanda" (boutons, onglet actif, badges sur une dizaine d'écrans), une portée largement au-delà d'un changement de logo qui n'a pas été demandé.

Vérifié : `tsc` (racine + `mobile/`) et `eslint` au vert ; capture Playwright de la landing et de `/prezzi` confirmant le nouveau logo et le wordmark "Tavolino" partout, y compris dans le footer sombre (contraste or-sur-vert vérifié lisible) et le copyright bas de page (dérivé de `APP_NAME`, donc mis à jour automatiquement).

## 13. Ce qui reste fragile ou à surveiller (issu de la revue des étapes 1 à 5, du durcissement post-Phase 0, et du passage nom + design)

- **Sélecteur de langue : les pages internes du dashboard et les corps de `/prezzi`/`/chi-siamo`/`/contatti` restent en français/italien quelle que soit la langue choisie** (voir §12.30). Seuls la coquille du dashboard (nav, rôle) et la nav/pied de page partagés sont traduits partout — un visiteur qui choisit l'espagnol depuis la landing puis se connecte verra un dashboard dont la barre latérale est en espagnol mais dont chaque page (menu, commandes, tables, staff, facturation, marque, analytics) reste en français. À compléter dans une passe dédiée, dictionnaire par dictionnaire comme fait pour la landing/l'authentification.
- **Envoi d'email : câblé mais jamais exercé contre un vrai compte** (voir §12.16). `RESEND_API_KEY`/`EMAIL_FROM` non définis dans cet environnement — le lien d'invitation manuel reste le chemin réellement testé. À vérifier en vrai (mode test/sandbox du provider) avant un pilote.
- **Email globalement unique pour les comptes staff** (voir §12.2.3) : une personne travaillant dans deux restaurants ne peut pas avoir le même email des deux côtés. Non bloquant pour le MVP, mais à concevoir explicitement si le besoin apparaît (compte multi-organisation) plutôt que de le découvrir en production.
- **`DIRECT_DATABASE_URL` (rôle `app_migrator`) ne doit jamais être utilisé par le code applicatif.** Prisma Client ne s'en sert qu'au moment des migrations, jamais à l'exécution — mais c'est une convention à faire respecter en revue de code, pas quelque chose que la base empêche mécaniquement si quelqu'un l'utilisait par erreur dans une future route API.
- **Sept fonctions `SECURITY DEFINER`** (`create_organization_and_owner`, `auth_lookup_user`, `accept_invitation`, `invitation_lookup_by_token`, `resolve_table_by_qr_token`, et depuis §12.18 `oauth_authenticate`, `verify_email_token`) sont la seule surface qui contourne RLS. Elles sont volontairement étroites, mais toute nouvelle fonction de ce type doit être traitée avec la même rigueur : elle est par construction en dehors de la garantie décrite en §12.3.
- **Vérification d'email : nudge, pas une porte** (§12.18). Une adresse peut toujours créer un compte sans jamais cliquer le lien de confirmation — rien n'est bloqué pour un compte non vérifié aujourd'hui, juste une bannière dans le dashboard. À décider explicitement si un vrai contrôle d'accès doit un jour en dépendre (par exemple, restreindre l'envoi d'invitations staff à un compte vérifié) — pas fait par défaut pour ne pas casser un onboarding existant.
- **Google/Apple, DeepL, OpenAI Images : câblés mais jamais exercés contre de vrais comptes** (§12.18) — même pattern que Stripe/email/S3 depuis le début de ce document. `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`, `APPLE_CLIENT_ID`/`APPLE_TEAM_ID`/`APPLE_KEY_ID`/`APPLE_PRIVATE_KEY`, `DEEPL_API_KEY`, `OPENAI_API_KEY` tous absents dans cet environnement. Chaque chemin de repli (bouton "indisponible", message "non configuré", 501 propre) est réellement testé ; le chemin heureux ne peut pas l'être sans vraies clés.
- **Paiement client en ligne : même compte Stripe que l'abonnement du restaurateur, pas Stripe Connect** (§12.18). L'argent d'une commande payée en ligne atterrit sur le solde de la PLATEFORME, pas sur celui du restaurant — acceptable pour cette passe (jamais testé contre un vrai compte de toute façon) mais bloquant pour un vrai lancement commercial : chaque organisation doit pouvoir encaisser ses propres commandes. À traiter avant tout pilote qui utiliserait réellement ce bouton.
- **Inscription OAuth ne collecte pas de nom de restaurant** (§12.18) — un premier "Continuer avec Google" crée une organisation au nom placeholder ("Restaurant de {nom}"), et il n'existe encore aucun champ dans le dashboard pour la renommer. À construire avant que ce chemin d'inscription soit mis en avant publiquement.
- **Le magasin de limitation de débit est en mémoire, un seul processus** (§12.8) — comme le temps réel (§12.6), à revoir ensemble si l'hébergement final est multi-instances.
- **Upload de photo/marque blanche : câblé mais jamais exercé contre un vrai bucket** (voir §12.16, §12.17). `S3_ENDPOINT`/`S3_BUCKET`/`S3_ACCESS_KEY_ID`/`S3_SECRET_ACCESS_KEY`/`S3_PUBLIC_URL_BASE` non définis dans cet environnement — seul le chemin de repli (URL manuelle pour les photos de plats, message d'erreur clair pour la marque blanche) est réellement testé. `uploadImage()` (§12.17) est le même client S3 pour les deux usages : une fois vérifié contre un vrai bucket R2/Supabase Storage, les deux chemins le sont en même temps.
- **Le temps réel suppose un processus Node long-vivant** (voir §12.6) — pas compatible tel quel avec un hébergement serverless par défaut (Vercel Functions). À trancher avec le choix d'hébergement définitif (§12.4), pas avant.
- **N'importe quel membre du staff peut faire passer n'importe quelle commande à n'importe quel statut**, y compris l'annuler. Volontaire pour cette étape (server et kitchen doivent pouvoir agir vite, sans se heurter à une permission trop fine) mais pas de piste d'audit : impossible de savoir qui a annulé quoi. À revoir si des restaurateurs pilotes signalent un problème réel de coordination interne — pas avant.
- **RGPD** : le schéma des `organizations`/`users` est prêt à recevoir une base légale de traitement documentée et un droit à l'effacement, mais ni l'un ni l'autre n'est implémenté (pas de mentions légales, pas d'endpoint de suppression de compte) — attendu pour avant le premier paiement (§10). Le client final qui commande via QR est, lui aussi, une personne dont on traite des données (commande horodatée, éventuellement des notes en texte libre) sans base légale documentée ni mention affichée sur la page publique.
- **Stripe n'a jamais tourné contre un vrai compte** (voir §12.7, §12.24) — le code est en place et vérifié dans la mesure du possible sans identifiants, mais un vrai parcours de paiement (mode test) reste à dérouler une fois avant tout pilote payant, sur les quatre durées d'engagement (§12.24).
- **Pas d'application du statut d'abonnement.** Un essai expiré ou un abonnement `past_due`/`canceled` ne bloque rien aujourd'hui — l'organisation garde un accès complet à toutes les fonctionnalités quel que soit `subscription_status`. Choix délibéré pour cette étape (verrouiller l'accès sur une intégration Stripe non testée en conditions réelles aurait été prématuré et risqué de bloquer un pilote par erreur) mais à trancher explicitement avant la Phase C (test média) : qu'est-ce qui se passe vraiment quand l'essai se termine ?
- **"mbQr" n'a subi aucune des quatre vérifications que §2 lui-même liste comme obligatoires** (TMview, UIBM, domaine, stores). Utilisable comme nom de travail pendant le reste du build ; à vérifier avant la Phase B, pas avant — mais ne pas oublier que ça n'a pas été fait, précisément parce que rien dans le produit ne le rappellera tout seul.
- **Les captures d'écran de la landing (`public/screenshots/`, §12.10) se périment.** Ce sont de vraies captures de l'app à un instant donné (menu de démo, tableau de commandes) — un futur changement visuel du dashboard ou du menu public les rendra visuellement en décalage avec le vrai produit. Pas d'automatisation qui les régénère : à refaire manuellement (`Playwright` + jeu de données de démo, voir §12.10) après tout changement notable de ces pages, et certainement avant la Phase A. Régénérées le 28 juillet 2026 sous la palette `DESIGN.md` (§12.14), puis à nouveau le 29 juillet 2026 sous la direction « Comanda » (§12.17) ; se repérimeront au prochain changement visuel notable.
- **La vidéo démo (`public/videos/`, §12.13) a la même limite, en pire** : un enregistrement, pas une capture statique, donc plus long à refaire (script Playwright avec `recordVideo` + repasse `ffmpeg`) si le parcours de commande change visuellement. À régénérer avant la Phase A également, et chaque fois que `/menu/[qrToken]` change d'apparence de façon notable. Régénérée le 28 juillet 2026 (§12.14), puis à nouveau le 29 juillet 2026 sous la direction « Comanda » (§12.17), même limite pour la suite.
- **Pas de témoignages clients sur la landing, volontairement** (§12.10) — à ajouter une fois de vrais retours de pilotes existent (Phase A), jamais avec des noms inventés.
- **App mobile : jamais compilée pour iOS dans cet environnement** (§12.19) — pas de macOS/Xcode ici. Le code est écrit et câblé (mêmes routes API, mêmes composants) mais n'a jamais tourné sur un simulateur ni un appareil iOS réel. Seul l'export web Metro (technique de test, jamais une cible livrée) et l'export Android ont pu être vérifiés par bundling.
- **App mobile : notifications push jamais livrées à un vrai appareil** (§12.19) — nécessite un identifiant de projet EAS réel (`app.json` → `extra.eas.projectId`), absent ici. Le mécanisme est vérifié dans sa mécanique (écriture en base, appel HTTP réel vers l'endpoint Expo sans erreur) mais jamais la réception effective. `registerForPushNotifications()` échoue silencieusement sans configuration, ne bloque jamais la connexion.
- **App mobile : polices exactes du web non reprises** (§12.19) — conflit de dépendances (`@expo-google-fonts/*` vs les dépendances web-only d'`expo-router`) non résolu, police système en approximation à la place. À reprendre une fois ce conflit réglé en amont (nouvelle version d'`expo-router`, ou fork/allègement des dépendances concernées).
- **Pas de fichier Figma.** Le logo (§12.9) existe en SVG dans le code, pas dans un outil de design — Figma n'est pas connecté à cet environnement. Si quelqu'un d'autre doit itérer visuellement dessus (variantes, retouche par un designer), il faudra soit connecter Figma, soit reconstruire le mark depuis `src/components/logo.tsx`.
